# BinMind 补齐模块实现说明

> 基于 2026-08-03 审查报告中的 P0/P1 缺口，实现的 13 个核心模块 + 文档 + 测试。

## 模块清单

### 模块 A: 基础信息采集

| 文件 | 行数 | 核心功能 |
|------|------|---------|
| `core/checksec.py` | ~200 | NX/PIE/Canary/RELRO/FORTIFY 检测，ELF/PE/Mach-O 三格式支持 |
| `core/plt_scanner.py` | ~180 | PLT/GOT 解析，危险函数自动标记，双重回退解析 |
| `core/libc_identifier.py` | ~220 | libc 版本指纹，多层回退（字符串→指纹→在线→系统） |
| `core/binary_profile.py` | ~200 | pwnpasi 风格综合画像，六维评估，利用策略推荐 |

**创新点**: `checksec.py` 不依赖外部 checksec.sh，纯 Python 解析 ELF Program Headers 和 Dynamic Section。`libc_identifier.py` 结合编译时字符串指纹和运行时符号偏移，比单一字符串匹配更健壮。`binary_profile.py` 自动生成利用策略建议（基于保护措施+可利用函数的规则推理）。

### 模块 B: 漏洞自动化分析

| 文件 | 行数 | 核心功能 |
|------|------|---------|
| `core/stack_overflow_analyzer.py` | ~280 | angr 符号执行计算 padding，canary 检测，静态回退分析 |
| `core/format_string_detector.py` | ~320 | 三级检测（静态→符号执行→LLM），偏移计算，利用建议 |

**创新点**: `stack_overflow_analyzer.py` 实现了符号执行+静态分析的双重回退机制——angr 计算精确 padding，angr不可用时从反编译代码中提取缓冲区声明估算。`format_string_detector.py` 的三级检测链参考了 PwnGPT 的"分析-生成-验证"范式，但将其限定在格式化字符串专项分析中以控制 LLM 调用成本。

### 模块 C: 验证闭环

| 文件 | 行数 | 核心功能 |
|------|------|---------|
| `core/exploit_executor.py` | ~250 | 沙箱执行（subprocess/Docker/dry-run），崩溃解析，成功判定 |
| `core/feedback_loop.py` | ~280 | LLM 驱动的迭代修正，重复错误检测，最多5轮 |
| `core/crash_analyzer_llm.py` | ~260 | LLM 深度崩溃分析，chain-of-thought 根因推理，批量分析 |

**创新点**: `feedback_loop.py` 实现了"重复错误检测"机制——连续3次相同错误签名则提前终止，避免 LLM 在死胡同中循环。`crash_analyzer_llm.py` 输入反编译代码+寄存器+栈回溯，比传统关键词匹配提供更细粒度的根因链。

### 模块 D+E+F: 管理与支撑

| 文件 | 行数 | 核心功能 |
|------|------|---------|
| `core/sample_manager.py` | ~260 | 样本 CRUD，批量扫描，CSV/Markdown 导出 |
| `core/experiment_tracker.py` | ~300 | 实验记录，四维评估，SQLite 持久化 |
| `core/adaptive_scheduler.py` | ~220 | ε-greedy MAB 方法选择，UCB 上置信界，奖励函数 |
| `core/cfg_extractor.py` | ~250 | 函数/调用图 CFG，angr/r2双重后端，DOT/JSON导出 |
| `scripts/batch_analyze.py` | ~180 | 批量分析，并行执行，汇总报告 |

**创新点**: `adaptive_scheduler.py` 将模糊测试/符号执行/LLM分析视为可竞争资源，通过多臂老虎机在线学习各方法在不同样本上的边际效用。参考了 Böhme 等 (2021) 的 fuzzing 成本模型和 Li 等 (2010) 的 contextual bandit 方法。`experiment_tracker.py` 的四维评估指标直接对应申报书 §5.3 第四条的要求。

## 管线集成

### 调用顺序

```
run_pipeline(binary_path)
  │
  ├─ get_binary_info()          [已有]
  ├─ detect_checksec()          [新增 A] ← 注入点1
  ├─ scan_plt()                 [新增 A]
  ├─ identify_libc()            [新增 A]
  ├─ build_binary_profile()     [新增 A] ← 注入点2: 统一画像
  │
  ├─ decompile_function()       [已有]
  ├─ ai_analyze_function()      [已有]
  ├─ extract_cfg()              [新增 F] ← 注入点3: CFG增强LLM上下文
  │
  ├─ analyze_stack_overflow()   [新增 B] ← 注入点4: 栈溢出专项
  ├─ detect_format_string_vulns()[新增 B] ← 注入点5: 格式化字符串专项
  │
  ├─ select_methods()           [新增 E] ← 注入点6: 自适应调度
  ├─ run_symbolic() / fuzzing   [已有+调度]
  │
  ├─ analyze_crash_with_llm()   [新增 C] ← 注入点7: LLM崩溃分析
  ├─ generate_exploit()         [已有]
  ├─ execute_exploit()          [新增 C] ← 注入点8: 执行验证
  ├─ run_feedback_loop()        [新增 C] ← 注入点9: 反馈迭代
  │
  ├─ write_report()             [已有]
  └─ [experiment_tracker 记录]  [新增 D]
```

### 数据传递

所有新模块接受和返回标准 Python dict，通过 `**kwargs` 或显式参数在管线中传递：

```python
# 示例：在 run_pipeline 中集成新模块
from core.checksec import detect_checksec
from core.binary_profile import build_binary_profile

checksec_result = detect_checksec(binary_path)
profile = build_binary_profile(
    binary_path,
    checksec=checksec_result,
    plt_entries=plt_entries,
    libc_info=libc_info,
)
result['binary_profile'] = profile  # 注入管线结果
```

## 运行示例

### 单文件分析
```bash
binmind analyze ./samples/ctf/stack_bof --symbolic --exploit
```

### 批量分析
```bash
python scripts/batch_analyze.py ./samples/ctf/ -o ./results/ --parallel
```

### Python API
```python
from core.checksec import detect_checksec
from core.binary_profile import build_binary_profile
from core.stack_overflow_analyzer import analyze_stack_overflow

profile = build_binary_profile('vuln_binary')
result = analyze_stack_overflow('vuln_binary', 'vuln', libc_info=profile['libc'])
print(f"padding={result['padding']}, strategy={result['strategy']}")
```

### 反馈环
```python
from core.feedback_loop import run_feedback_loop

loop_result = run_feedback_loop(
    binary_path='./vuln_binary',
    initial_script=open('exploit.py').read(),
    checksec=checksec_result,
    max_iterations=5,
)
if loop_result['success']:
    print(f"Exploit succeeded after {loop_result['iterations']} iterations")
```

## 已知限制

| 模块 | 限制 | 缓解措施 |
|------|------|---------|
| checksec | PE 的 Canary 检测精度有限 | pefile 库加载 LoadConfig 目录 |
| plt_scanner | stripped 二进制需 r2 高级分析 | 回退到 pyelftools 直接解析 .dynsym |
| libc_identifier | 无本地 libc-database 时依赖在线查询 | 系统 libc 回退 + 经验偏移估算 |
| stack_overflow_analyzer | angr 对大型二进制可能超时 | 静态回退 + 超时控制 (ANGR_TIMEOUT) |
| format_string_detector | x86_64 偏移计算保守（默认6） | 符号执行精确计算，LLM 辅助纠正 |
| exploit_executor | Docker 沙箱需要预构建镜像 | subprocess 回退，dry-run 语法检查 |
| feedback_loop | LLM 可能生成语法错误的脚本 | py_compile 语法预检查 + 迭代修正 |
| adaptive_scheduler | 冷启动时各方法臂无先验信息 | ε-greedy 探索 + UCB 上置信界 |

## 未来改进方向

1. **libc 数据库本地部署**: 集成 niklasb/libc-database 的离线查询
2. **强化学习调度器**: 用 DQN 替代 ε-greedy MAB（需更多训练数据）
3. **多架构栈溢出**: 当前符号执行路径以 x86_64 为主，需扩展 ARM/MIPS 支持
4. **自动 Canary 泄露**: 当前仅检测 canary 存在性，未自动搜索泄露路径
5. **并行验证**: 反馈环中尝试多个 LLM 修正方案并行执行（多臂修正）
